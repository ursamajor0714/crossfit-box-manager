# 보충자료 필요 열 · 운동방향성/부상 수정칸 (2026-09-18)

## 보충자료 필요 (회원 목록)

회원 목록에서 **지운 운동복 열 자리**에 `보충자료 필요` 열을 만들었다.
그 회원의 상세 정보 중 비어 있는 칸을 주황색 배지로 보여준다.

대상은 네 가지 — **인스타 · 사진 · 운동방향성 · 부상/특이사항**.
공백만 들어 있는 칸도 비어 있는 것으로 본다. 다 채워져 있으면 `-` 만 뜬다.

판정은 `missingInfoFields()` 한 곳에서만 한다. 목록과 상세가 서로 다른 기준을 쓰지 않도록,
받을 항목이 늘면 `SUPPLEMENT_FIELDS` 배열에만 추가하면 된다.

표가 7칸에서 8칸이 됐으므로 빈 목록 `colspan` 도 같이 고쳤고, 레포의 표 20개를 다시 검사해
헤더 칸 수와 `colspan` 이 전부 맞는 것을 확인했다.

## 운동방향성 · 부상/특이사항 수정칸

회원 상세 > `정보 수정` 탭의 **메모 바로 윗줄**에 좌우 두 칸으로 넣었다.
기존에 입력된 값이 있으면 그대로 채워져서 열린다 (계약서 작성 때 회원이 쓴 내용).

### 함께 고친 것 — 저장되지 않고 버려지던 값들

`PUT /api/members/:id` 가 `birth_date` 를 받지 않고 있었다. **정보 수정 화면은 생년월일을
보내고 있었는데 서버가 그 값을 무시**해서, 고쳐도 저장이 안 되고 조용히 사라지고 있었다.
이번에 추가한 `goal`·`injury` 와 함께 `birth_date` 도 저장하도록 고쳤다.

## 홈에서 돈을 전부 뺐다

홈 최하단의 `📈 월별 매출 추이` 카드를 화면·스크립트·스타일에서 지웠다.

처음에는 그 카드 머리에 있던 `이번 달 매출` 숫자를 상단 지표 줄로 옮겼는데,
**사용자가 바로 잡았다 — 홈은 코치와 함께 보는 화면이라 매출·금액이 보이면 안 된다.**
그래서 지표도 없앴다.

화면에서 지우는 것으로 끝내지 않고 **서버 응답에서도 뺐다.** `GET /api/stats` 는 이제
`monthly_amount` 를 계산하지도, 내려주지도 않는다. 화면에서만 숨기면 개발자 도구나
API 직접 호출로 그대로 보이기 때문이다.

같은 이유로 두 가지를 더 고쳤다.

- **요금표 조회에 권한을 붙였다.** `GET /api/pricing` 도 결국 금액이라, 등록·재등록·계약서·
  가격표 권한 중 하나라도 있어야 내려준다. `홈` 만 허용된 코치는 403이다.
  (등록 폼은 요금표가 필요하므로 넓게 열되, 홈만 있는 코치에게는 닫는다.)
  요금표를 못 읽어도 홈이 깨지지 않도록 `loadPricingData()` 가 조용히 넘어가게 했다.
- **홈의 만료 임박 목록이 회원 행 전체를 내려주고 있었다.** `SELECT m.*` 이라
  비밀번호 해시·메모까지 함께 나갔다. 화면이 실제로 쓰는 `id·이름·연락처·만료일·요금제`
  만 내려준다.

홈의 `오늘 방문 예정(드랍인·체험)` 위젯은 코치도 봐야 하므로 `홈` 권한으로 읽을 수 있게 했다.
이름·시간만 나오고 금액은 없다.

`GET /api/revenue/monthly` 와 `/api/revenue/forecast` 는 **이제 아무도 부르지 않는다.**
지울지는 따로 정하면 된다 (지금 지워도 화면에 영향 없음).

## 함께 고친 것 — 활성 회원 수에 코치가 섞였다

코치도 `members` 테이블에 들어가므로 홈의 `활성 회원` 이 코치까지 세고 있었다.
회원권을 사는 사람이 아니므로 뺐다 (코치 2명 포함 6명 → 4명으로 확인).

# 정보 수정에서 사진 올리기 · 렌더/네온 부담 정리 (2026-09-18)

## 계약서의 사진은 어떤 방식이었나 (확인 결과)

**파일 업로드가 아니라 카메라로 직접 촬영하는 방식이다.**

`startCamera()` 가 `navigator.mediaDevices.getUserMedia` 로 카메라를 켜서 `<video>` 를 띄우고,
`takePhoto()` 가 그 영상을 **320×320 정사각형으로 가운데만 잘라** 캔버스에 그린 뒤
`canvas.toDataURL('image/jpeg', 0.7)` 로 base64 문자열을 만든다. 그 문자열이 그대로
`members.photo` (TEXT 컬럼)에 들어간다. **파일 서버나 S3 없이 DB 안에 글자로 저장된다.**

이 코드는 `fa166d3 Initial commit` (2026-07-03) 에 이미 들어 있었다 — 1.0.0 에 해당한다.

## 정보 수정 탭의 사진

관리자 화면은 데스크톱에서도 쓰므로 **파일 선택**(`<input type="file" accept="image/*">`)으로 받는다.
휴대폰에서는 같은 버튼이 카메라 촬영도 같이 띄워 준다.

**저장 규격은 계약서와 똑같이 맞췄다** — 브라우저에서 320×320 가운데 자르기, jpeg 0.7, base64.
두 경로가 다른 크기로 저장되면 목록 무게가 제각각이 되기 때문이다.

미리보기·사진 삭제 버튼을 두고, 삭제는 `저장 완료` 를 눌러야 실제로 반영된다.

## 사용자 지적 — "렌더 터지지 않냐?"

맞는 지적이었다. **사진 자체가 아니라 회원 목록이 전원 사진을 다 내려주는 것이 문제**였다.

`GET /api/members` 가 `SELECT m.*` 이라 **모든 회원의 사진 본문**이 목록 응답에 들어가고 있었다.

| 회원 수 | 전원 사진이 있을 때 목록 응답 |
|---|---|
| 100명 | 약 2.4MB |
| 300명 | 약 7.3MB |
| 500명 | 약 12.2MB |

Render 무료 인스턴스 메모리로는 위험한 크기다. 회원 목록을 열 때마다 이만큼이 오간다.
**이미 있던 문제**였고(계약서로 등록된 회원은 이미 사진이 있다), 정보 수정에서도 사진을 올릴 수
있게 하면 사진 있는 회원이 늘어 더 빨리 부딪힌다.

### 고친 것

- **목록에서 사진 본문을 뺐다.** 대신 `has_photo` (0/1)만 보낸다. 목록이 사진으로 하는 일은
  `보충자료 필요` 판정뿐이라 있으면 된다. 사진 자체는 상세(`/api/members/:id`)에서 한 명 것만 받는다.
  확인: 24KB짜리 사진을 넣어도 목록 응답은 3.6KB 그대로였다.
- **목록에서 비밀번호 해시도 같이 빠졌다.** `SELECT m.*` 이라 그동안 함께 나가고 있었다.
  이제 화면이 실제로 쓰는 칸만 내려준다.
- **사진 크기·형식을 서버에서 검사한다.** 화면은 320으로 줄여 보내지만 API 를 직접 부르면
  원본이 그대로 올 수 있다. `data:image/(jpeg|png|webp);base64,` 형식만, **400KB 이하**만 받는다.
- **사진을 안 보낸 저장 요청은 사진을 건드리지 않는다.** `'photo' in req.body` 일 때만 갱신한다.
  안 그러면 사진을 안 보내는 다른 호출이 멀쩡한 사진을 지운다.

### 네온(DB) 쪽은 괜찮다

한 장이 20~30KB이므로 회원 500명이 전부 사진을 가져도 약 15MB다. Neon 무료 용량(0.5GB)에
비하면 여유가 있다. 부담은 **저장 용량이 아니라 목록 응답 크기**였고, 그쪽을 고쳤다.

|---|---|
| 사진 저장 · 교체 · 삭제 | ✓ |
| 사진을 안 보낸 저장이 기존 사진을 지우지 않음 | ✓ |

# 사진 촬영 전용 · 계약서 사진 중복 정리 (2026-09-18)

## 1. 파일 업로드를 빼고 촬영만 남겼다

처음에는 관리자 화면이 데스크톱에서도 쓰인다는 이유로 파일 선택(`<input type="file">`)으로 넣었는데,
사용자 지시로 **계약서와 똑같이 카메라 촬영만** 받도록 바꿨다. 회원 식별용 사진이므로
아무 이미지 파일이나 올라가면 안 되고, 휴대폰으로 접속하면 그 자리에서 찍는 게 원래 흐름이다.

정보 수정 탭의 버튼: `📷 카메라 켜기` · `촬영` · `🔄 전/후면` · `사진 삭제`.
카메라를 켜면 미리보기 칸이 92px에서 200px로 커지고, 찍으면 다시 작아지며 사진으로 바뀐다.

**카메라를 켜 둔 채 모달을 닫거나 다른 탭으로 가면 반드시 끈다.** 안 그러면 카메라 불이 계속
켜져 있다. 탭 전환(`switchMemberTab`)과 모달 닫기(`closeModal`) 양쪽에 껐다.
카메라를 못 쓰는 기기에서는 "카메라가 있는 기기에서 열어 달라"는 안내가 뜬다.

## 2. 규격을 한 곳으로 모았다 — `frontend/public/js/photo-capture.js`

계약서와 관리자 화면이 각자 카메라 코드를 들고 있으면 **저장 크기가 갈라진다.** 실제로 이번에
파일 업로드로 먼저 만들었을 때 규격을 손으로 맞춰야 했다.

공용 파일에 세 가지만 둔다.

| 함수 | 하는 일 |
|---|---|
| `openSquareCamera(preview, facing)` | 카메라를 켜서 미리보기에 `<video>` 를 붙인다 |
| `captureSquarePhoto(preview, facing)` | 지금 화면을 320×320 정사각형으로 잘라 base64 jpeg 로 만든다 |
| `stopStream(stream)` | 카메라를 끈다 |

크기(320)와 품질(0.7)도 이 파일에만 있다. **계약서 화면도 이 함수를 쓰도록 바꿨고**, 버튼을
갈아끼우는 부분만 각 화면에 남겼다. 전면카메라를 거울로 보여주고 저장할 때 좌우를 되돌리는
처리도 공용 함수 안에 있다.

계약서 쪽 동작이 바뀌지 않았는지 **가짜 카메라로 따로 확인했다** (5개 통과).

## 3. 같은 사진이 두 벌 쌓이던 것 정리

계약서를 제출하면 사진이 `contracts.photo` 에 저장되고, 관리자가 그 계약서로 회원을 등록하면
같은 사진이 `members.photo` 에도 복사됐다. **한 장에 20~30KB 짜리가 회원마다 두 벌**이었다.

- **등록이 끝나면 계약서 쪽 사본을 비운다.** 단, **회원 쪽에 사진이 실제로 들어갔을 때만** 비운다
  — 아니면 사진이 아예 사라진다. (사진 없이 등록한 경우는 계약서 사진을 그대로 둔다.)
- **계약서 상세에서는 연결된 회원의 사진을 대신 보여준다.** 화면상 달라지는 것은 없다.
- **계약서 목록의 📷 표시**도 연결된 회원에게 사진이 있는지까지 보고 판단한다. 안 그러면
  등록이 끝난 계약서에서 아이콘이 사라진다.
- **기존에 쌓인 것도 한 번 정리했다.** 서버가 뜰 때 회원 쪽에 사진이 있는 등록 완료 계약서만
  골라 사본을 비운다 (`backend/db.js`). 조건이 붙어 있어 여러 번 돌아도 안전하다.
- 직원등록으로 만든 계약서도 같은 처리를 한다.

주의: 회원 사진을 지우면 그 계약서에서도 사진이 안 보이게 된다. 사본을 없앴기 때문이다.

# 보충자료가 채우면 정말 빠지는지 확인하다 발견한 것 (2026-09-18)

사용자 질문: **"보충자료 레이블이 채워지면 보충자료 필요에서 삭제되게끔 설계된거 맞지?"**

맞게 설계돼 있었지만, **확인해 보니 인스타만 빠지지 않았다.**

## 원인 — 인스타는 채울 방법이 아예 없었다

`정보 수정` 탭에 **인스타 입력칸 자체가 없었다.** 상세의 기본 정보에는 보여주기만 하고,
`PUT /api/members/:id` 도 `insta` 를 받지 않았다.

즉 계약서 작성 때 회원이 직접 적은 값이 아니면 인스타는 영원히 비어 있고,
`보충자료 필요` 에 계속 떠 있는데 **관리자가 채울 방법이 없는 상태**였다.
"보충자료 필요"는 채워 넣으라고 만든 표시인데 정작 그 칸만 채울 수가 없었던 셈이다.

## 고친 것

- `정보 수정` 탭 **지역 다음에 인스타그램 칸**을 넣었다. 기존 값이 있으면 채워져서 열린다.
- `PUT /api/members/:id` 가 `insta` 를 저장한다.

이제 보충자료 네 칸(인스타·사진·운동방향성·부상/특이사항)이 **전부 정보 수정에서 채워진다.**

## 확인 — 하나씩 채우며 실제로 줄어드는지

실제 API로 저장하고, 판정은 화면이 쓰는 `missingInfoFields()` 를 소스에서 그대로 떼어내 돌렸다.

| 단계 | 보충자료 필요 |
|---|---|
| 시작 (네 칸 다 빔) | 인스타 · 사진 · 운동방향성 · 부상/특이사항 |
| 인스타 채움 | 사진 · 운동방향성 · 부상/특이사항 |
| 운동방향성 채움 | 사진 · 부상/특이사항 |
| 부상/특이사항 채움 | 사진 |
| 사진 촬영 | **(없음)** |
| 사진 삭제 | 사진 (다시 뜬다) |
| 인스타에 공백만 입력 | 인스타 (채운 것으로 치지 않는다) |

목록은 `has_photo`, 상세는 `photo` 로 판단하는데 **두 기준 모두 같은 결과**가 나오는 것까지 확인했다.
저장하면 `saveMember()` 가 `loadMembers()` 로 목록을 다시 읽으므로 화면에서도 바로 사라진다.

# 인스타 아이디는 이미 받는 칸이 있었다 (2026-09-18)

앞 절에서 "인스타는 채울 방법이 없다"며 `정보 수정` 에 인스타 칸을 새로 넣었는데,
사용자가 바로 잡았다.

> **"뭔소리야 가입경로 인스타 선택하면 인스타 아이디 입력 뜨잖아"**

맞는 지적이다. `정보 수정` 의 **추가 정보** 칸(`e-source-detail`)이 가입경로에 따라 라벨을 바꾼다
— 인스타면 `인스타 아이디`, 네이버면 `네이버 아이디`, 지인이면 `지인 이름`, 양도면 `양도한 사람 이름`.
**내가 만든 칸은 중복이라 되돌렸다.**

## 확인해 보니 인스타 아이디가 들어가는 곳이 둘이다

| 컬럼 | 어디서 받나 | 누구에게 |
|---|---|---|
| `members.insta` | 계약서 1단계 `인스타그램 아이디`, 관리자 등록 폼 | 가입경로와 무관하게 누구나 |
| `members.source_detail` | 정보 수정의 `추가 정보` (가입경로가 인스타일 때) | 인스타로 들어온 회원 |

더미데이터의 `정만료` 는 가입경로가 오프라인인데 `insta` 가 있다. 즉 두 칸은 실제로 쓰임이 다르다.

## 보충자료 판정 규칙

- **인스타로 들어온 회원(`source === '인스타'`)에게만** 인스타 아이디를 요구한다.
  지인·오프라인으로 들어온 회원에게 인스타 아이디를 보충자료로 요구할 이유가 없다.
- 판정은 **두 칸 중 하나라도 있으면 채워진 것**으로 본다. 계약서에서 적었으면 `insta` 에,
  나중에 관리자가 채우면 `source_detail` 에 들어가기 때문이다.
- 상세의 `인스타그램` 표시도 같은 기준으로 바꿨다 — 가입경로가 인스타면 `source_detail` 을 보여준다.

배지 이름도 `인스타` 에서 **`인스타 아이디`** 로 바꿨다. 어느 칸을 채우라는 것인지 분명해진다.

## 확인 (10가지)

| 경우 | 결과 |
|---|---|
| 가입경로 인스타 + 둘 다 빔 | `인스타 아이디` 필요 |
| 가입경로 인스타 + `추가 정보` 채움 | 빠진다 |
| 가입경로 인스타 + `insta` 채움 (계약서에서 적은 경우) | 빠진다 |
| 가입경로 지인 | 요구하지 않는다 |
| 가입경로 지인 + 지인 이름이 적혀 있음 | 인스타로 치지 않는다 |
| 공백만 입력 | 안 채운 것으로 본다 |
