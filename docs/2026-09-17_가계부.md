# 가계부 (매출 관리 > 가계부 탭)

기존 `월별 통계 · AI 분석` 자리표시자 탭을 가계부로 교체했다.

## 화면 구성

- **왼쪽 = 매출(+)**: 회원권·락커·운동복·드랍인·체험 등 기존 매출 집계 + 가계부에서 직접 등록한 수입
- **오른쪽 = 지출(−)**: 기존 환불(매출의 마이너스 건) + 가계부에서 직접 등록한 지출
- **상단**: 기간 선택 버튼(달력) + 수입 합계 · 지출 합계 · 순익 카드
- **하단 입력줄**: 구분 아코디언(매출/지출) → 항목 아코디언(구분에 따라 목록이 바뀜) → 금액 → 상세 내역 → 고정비 체크박스 → 등록 버튼

아코디언은 라이브러리 없이 `<details>/<summary>` 로 만들었다. 바깥을 클릭하면 닫힌다.

## 매출과의 연결

두 방향 모두 연결했다.

- **매출 → 가계부**: 가계부 왼쪽 목록은 `buildRevenueItems()` 결과(기존 매출 내역 탭과 같은 소스)를 그대로 쓴다.
  금액이 마이너스인 건(환불)은 부호를 뒤집어 오른쪽 지출로 보낸다.
- **가계부 → 매출**: 가계부에서 `매출`로 등록한 항목은 `buildRevenueItems()` 안에서 합쳐지므로
  **매출 내역 탭과 매출 엑셀에도 그대로 잡힌다.** 자동 집계 건은 가계부에서 삭제할 수 없고
  (원본이 회원권·락커 기록이라서), 가계부에서 등록한 건만 × 버튼이 붙는다.

남은 부분: 홈 화면의 `월별 매출 추이` 그래프(`/api/revenue/monthly`)는 테이블을 직접 집계하므로
가계부 수동 매출이 반영되지 않는다. 필요하면 그때 붙인다.

## 기간 선택 (2차 작업)

기본값은 **한국시간 기준 당월**이다. 화면을 열면 이번 달만 보인다.

`기간: 2026년 9월` 버튼을 누르면 달력이 뜨고,

- `‹` `›` 로 달을 옮긴다 (아직 적용 안 됨)
- 날짜를 누르면 **그 하루만** 보는 일별 조회 — 같은 날을 다시 누르면 풀린다
- `이 달 전체` 는 날짜 선택을 풀어 그 달 전체로
- `전체 기간` 은 즉시 전체 조회
- `확인` 을 눌러야 위에서 고른 달/날짜가 실제로 적용된다

API는 `GET /api/ledger?month=YYYY-MM` (월별) 또는 `?date=YYYY-MM-DD` (일별),
둘 다 없으면 전체 기간이다. `date`가 오면 `month`는 무시하고 그 날의 달을 기준월로 쓴다.

달을 옮겨서 보다가 항목을 등록하면 그 기간에 남도록 날짜를 맞춘다
(일별 보기면 그 날, 이번 달이면 오늘, 지난 달이면 그 달 1일). 안 그러면 등록하자마자 화면에서 사라진다.

달력으로 대체돼서 월 드롭다운(`months` 응답 필드와 그 쿼리)은 지웠다.

## 삭제

가계부에서 직접 등록한 항목은 행 오른쪽 `삭제` 버튼으로 지운다.
(처음에는 `×` 아이콘이었는데 눈에 안 띄어서 글자 버튼으로 바꿨다.)

자동으로 넘어온 건(회원권·락커·운동복·환불)은 삭제 버튼이 없다.
원본이 회원 등록 기록이라 회원 관리 쪽에서 지워야 하고, 여기서 지우면 매출이 어긋난다.

## 고정비

`고정비로 등록 (매월)` 체크 시 DB에는 **한 건만** 저장하고, 조회할 때 등록월부터 기준월까지
매달 한 건씩 펼쳐서 보여준다(`backend/utils/ledger.js`의 `expandLedgerRows`).
그래서 고정비를 삭제하면 등록된 모든 달에서 함께 사라진다 — 삭제 확인창에 그렇게 적어뒀다.

날짜가 깨진 행 때문에 무한 루프가 나지 않도록 600개월에서 자른다.

## 바뀐 파일

| 파일 | 내용 |

## 항목 목록

- 매출: 회원권, 락커, 운동복, 드랍인, 체험, 물품판매, 강습·대관, 기타수입
- 지출: 환불, 임대료, 관리비, 공과금, 세금, 인건비, 물품구입, 장비·수리, 보험·수수료, 광고비, 기타지출

목록은 `backend/routes/stats.js` 상단의 `LEDGER_CATEGORIES` 한 곳에서만 고치면 화면까지 반영된다.

## 로컬 실행 (2026-09-17 기준)

운영 Neon DB를 건드리지 않으려고 도커에 빈 Postgres를 띄워서 확인했다.

```
docker run -d --name grove-pg -e POSTGRES_PASSWORD=grove -e POSTGRES_DB=grove -p 55432:5432 postgres:16-alpine
```

`.env` (gitignore 대상):

```
DATABASE_URL=postgres://postgres:postgres@localhost:55432/grove
ADMIN_PASSWORD=(로컬용 비밀번호를 직접 넣는다)
PORT=3000
```

이때 `backend/db.js`에 **DATABASE_URL이 localhost면 SSL을 끄는** 분기를 넣었다.
로컬 Postgres는 SSL이 없어서 이 분기가 없으면 서버가 뜨지 않는다. 운영(Neon)은 그대로 SSL을 쓴다.

## 검증한 것 / 안 한 것

검증함 (DB를 비우고 실제 API를 그대로 호출해서):

- **신규 회원 등록이 가계부에 잡히는지** — `POST /api/members` 로 김가계 님을 회원권 3개월 550,000(카드),
  락커 12번 3개월 90,000(현금), 운동복 3개월 60,000(계좌이체)으로 한 번에 등록했더니
  가계부 왼쪽에 세 건이 각각 `회원등록` / `락커` / `운동복` 으로 뜨고 수입 합계 700,000이 됐다.
  즉 회원 관리 화면에서 평소대로 등록하면 가계부에 따로 적을 필요가 없다.
- **환불이 지출로 넘어가는지** — `POST /api/members/2/refund` 로 200,000 환불 처리하니
  오른쪽 지출에 `환불 · 김가계 200,000`으로 잡혔다.
- 항목 목록 조회, 등록(매출/지출), 금액 0 이하 거부, 삭제, 없는 id 삭제 404, 미인증 401
- 고정비(2026-07-05 등록)가 9월 조회에서 2026-09-05로 펼쳐지는 것
- 일별 조회 — `?date=2026-09-17` 은 등록·환불 건만, `?date=2026-09-16` 은 그날 지출만 나온다
- 가계부에 등록한 물품판매 45,000이 매출 내역(`/api/revenue/all`)에도 잡히는 것
- `node backend/utils/ledger.js` 자체 점검 통과

검증 못 함:

- **브라우저에서 실제로 클릭해본 확인은 못 했다.** Claude in Chrome 확장이 꺼져 있어서 막혔다.
  화면 마크업(입력줄 9개 요소 + 달력)이 전부 렌더되는 것과 정적 파일 200은 확인했지만,
  아코디언·달력 클릭 동작은 눈으로 봐야 한다.

# 운동복 서비스 종료 화면 정리 (같은 날)

운동복 서비스가 끝나서 화면에서 치웠다.

| 위치 | 처리 |
|---|---|
| 홈 대시보드 `운동복 대여` 박스 | 삭제 (`frontend/views/admin.ejs`) |
| `admin-core.js`의 `stat-uniforms` 값 쓰는 줄 | 같이 삭제 — 안 지우면 없는 요소를 참조해서 **홈 통계 전체가 멈춘다** |
| 락커 페이지의 비활성 `운동복` 서브탭 | 삭제. 이제 상단 탭은 `락커` 하나만 남는다 |
| 매출 내역 탭의 `구분` 필터 `운동복` 옵션 | 삭제 |
| 가계부 매출 항목의 `운동복` | 삭제 (`LEDGER_CATEGORIES`) |

## 일부러 안 건드린 것

**과거 운동복 매출 기록은 그대로 뒀다.** `buildRevenueItems()`의 `uniform_history` 집계를 빼면
운동복을 팔던 달의 매출 총액이 지금 와서 줄어든다. 이미 정산이 끝난 달의 숫자가 바뀌는 셈이라
장부로서 맞지 않다고 봤다. 새로 등록할 수 없게만 막고, 과거 기록은 보존한다.

과거 기록까지 매출에서 빼려면 `backend/routes/stats.js`의 `buildRevenueItems()` 안
`4) 운동복 (uniform_history)` 블록을 지우면 된다.

`uniform-inner` 화면 블록과 운동복 등록/연장 모달, 회원 목록의 `운동복` 컬럼,
`/api/uniforms` 라우트는 남아 있다. 탭이 없어져 화면으로는 갈 수 없다.

# 작업 후 자체 점검에서 고친 것

전체를 다시 훑으면서 나온 문제와 처리.

## 1. 미래 달에서 순익이 틀리던 버그 (고침)

달력 `›` 로 다음 달을 보면 **고정지출은 나오는데 고정수입은 안 나왔다.** 순익이 그만큼 틀렸다.

원인: 고정 항목을 펼치는 기준월이 둘로 갈려 있었다.
지출은 조회 기준월(`upto`)까지 펼쳤는데, 수입은 `buildRevenueItems()` 안에서 **항상 이번 달까지만** 펼쳤다.

고침: `buildRevenueItems(uptoMonth)` 로 기준월을 받도록 하고 `/api/ledger`가 `upto`를 넘긴다.
인자 없이 부르면 이번 달이라 `/api/revenue/all`·엑셀은 그대로다 (매출 내역이 미래 건으로 부풀지 않게).

2026-11 조회에서 수입 300,000 / 지출 2,500,000 / 순익 −2,200,000 로 9월과 같게 나오는 것 확인.

## 2. 홈 통계가 멈출 뻔한 것 (고침)

홈의 `운동복 대여` 박스를 지우면서 `admin-core.js`에서 그 박스에 값을 쓰던 줄을 같이 지웠다.
안 지웠으면 없는 요소를 참조해서 **홈 통계 네 칸이 전부 안 뜬다.**

## 3. 전역 변수 이름 충돌 위험 (고침)

가계부 달력이 쓰던 `calMonth` / `calPick` 은 `index.js`·`visit.js` 에도 있는 이름이다.
지금은 관리자 페이지가 그 파일들을 안 불러서 문제가 없지만, 나중에 합쳐지면 같은 파일 스코프에서
`let` 이 두 번 선언돼 **스크립트 전체가 죽는다.** `ledgerCalMonth` / `ledgerCalPick` 로 바꿨다.

## 4. 매출 구분 필터에 빠져 있던 항목 (채움)

가계부에서 등록한 매출은 매출 내역 탭에도 잡히는데, `구분` 필터 드롭다운에는 그 이름들이 없어서
**목록에는 보이는데 필터로는 못 고르는** 상태였다. `회원권`·`물품판매`·`강습·대관`·`기타수입` 추가.

## 확인만 하고 안 건드린 것

- `loadUniforms()` 는 락커 환불 처리 등에서 아직 불린다. `uniform-inner` 화면 블록과
  `uniform-tbody` 를 남겨뒀기 때문에 요소를 못 찾아 죽는 일은 없다. (탭만 없어서 화면으로는 못 간다)
- 회원 등록 폼에는 운동복 입력이 이미 없다 (이전 `운동복 서비스 종료` 커밋에서 제거됨).
  즉 앞으로 운동복 매출이 새로 생길 경로는 없다.
- 회원 목록의 `운동복` 컬럼(`th-uniform`)과 정렬 기능은 그대로 둔다 — 이번 요청 범위 밖이다.
- `GET /api/stats` 응답의 `uniform_active` 필드는 쓰는 곳이 없어졌지만 남겨뒀다.
  지우려면 `backend/routes/stats.js` 에서 해당 쿼리와 필드를 같이 빼면 된다.
- 가계부 매출 중 결제수단이 없는 건은 매출 엑셀의 `결제수단별` 시트 집계에서 빠진다.
  이건 원래 결제수단 미입력 건의 동작과 같다 (전체 합계에는 들어간다).

## 점검 결과

전 엔드포인트 200 (`/api/stats`, `/api/ledger`, `/api/revenue/*`, `/api/lockers`, `/api/uniforms`, `/api/members`),
전 페이지 200, 매출 엑셀 생성 정상, 서버 로그 에러 없음, `node backend/utils/ledger.js` 통과.
점검에 쓴 데이터는 전부 지웠다.

# 매출 항목 정리 (같은 날, 사용자 지시)

- `강습·대관` 삭제, `기타수입` → `기타` 로 통합
- `체험` 삭제 — 무료라 0원짜리 행만 쌓인다. 매출 집계(`buildRevenueItems`)와 구분 필터, 가계부 항목에서 모두 뺐다.
- `운동복` 삭제 — 서비스 종료. 앞서 "과거 기록은 남긴다"고 했던 판단을 사용자 지시로 뒤집어
  `uniform_history` 집계 블록을 통째로 제거했다. **운동복을 팔던 달의 매출 총액이 그만큼 줄어든다.**

최종 매출 구성: 회원등록 · 드랍인 · 락커 · 환불 + 가계부에서 직접 등록한 매출(회원권/락커/드랍인/물품판매/기타)

엑셀의 `SOURCES` 목록과 분류별 시트 주석도 같이 맞췄다.
`admin-core.js`의 `badgeColor` 에 남은 `체험`·`운동복` 색상 키는 안 쓰이면 무시되므로 그대로 뒀다.

확인: 드랍인 30,000 / 체험 0원 / 운동복 60,000 을 넣고 조회하니 **드랍인 30,000만** 잡혔다. 엑셀도 정상 생성.
확인에 쓴 데이터는 지웠다.

# 회원 상세 > 락커 등록 + 항목 재조정 (같은 날)

## 락커 등록 탭

회원 상세 모달의 버튼 줄(재등록 / 메시지 보내기 / 메시지 이력 / 비번 초기화 / 환불 / 삭제)에
**`락커 등록`** 을 넣었다. 버튼이 7개가 되어 줄이 넘치므로 그 줄에 `flex-wrap:wrap` 을 줬다.

누르면 뜨는 모달(`member-locker-modal`):

1. **회원권 기간과 연동할까요?** — 현재 회원권 기간이 있을 때만 뜬다.
   `예` 를 누르면 락커 시작일·종료일을 회원권과 똑같이 맞추고 기간·날짜 입력을 잠근다.
   `아니오` 면 직접 고른다. 기본값은 `아니오`.
2. **락커 번호** — 비어있는 락커만 목록에 나온다.
3. **기간** — `1개월` / `3개월` / `6개월` / `기타 (직접 설정)`.
   기타를 고르면 종료일을 자동 계산하지 않고 직접 넣는다.
4. 시작일 · 종료일 · 금액 · 결제 수단

등록은 **기존 배정 API(`PUT /api/lockers/:id`)를 그대로 쓴다.** 새 엔드포인트를 만들지 않았다.
이 API가 `lockers` 의 `start_date`/`end_date` 를 실제로 바꾸고 `locker_history` 에 `배정` 으로
남기므로, 락커 실제 기간과 매출·가계부에 한 번에 반영된다.

코드는 `frontend/public/js/admin-facility.js` 맨 아래 (락커 도메인이라 파일을 새로 만들지 않았다).

검증: 회원권 2026-09-17~2026-12-17 로 회원을 만들고 연동 `예` 로 30번 락커를 등록하니
락커 기간이 회원권과 정확히 같아졌고, 가계부 9월에 `회원등록 550,000` + `락커 90,000` 으로 잡혔다.

## 운동복 — 과거 기록 되살림 (앞선 결정 번복)

바로 앞에서 `uniform_history` 집계를 통째로 뺐는데, 사용자가 **"과거 건은 건드리지 말고
업데이트 시점부터만 영향가게"** 로 다시 지시해서 집계를 되돌렸다.

- 과거 운동복 매출은 매출 내역·가계부·엑셀에 그대로 잡힌다 (8월 60,000 확인).
- 등록 화면이 없고 가계부 항목에도 없으므로 **새 운동복 매출이 생길 경로는 없다.**
- 엑셀 `SOURCES` 목록에도 `운동복` 을 다시 넣었다.
- 다만 매출 내역 탭의 `구분` 필터에는 `운동복` 을 넣지 않았다. 과거 행은 목록에 보이지만
  필터로 따로 고를 수는 없다. 필요하면 옵션 한 줄만 되살리면 된다.

체험은 0원이라 총액에 영향이 없어서 뺀 상태 그대로 둔다.

# 락커 금액 자동계산 · 홈 목록 높이 (같은 날)

## 락커 월 요금은 5,000원

작업 중에 테스트로 넣었던 3개월 90,000원(월 30,000원)은 **틀린 값**이었다.
계약서(`frontend/views/contract.ejs`)에 "개인락커(월 5,000원)"으로 명시돼 있고,
신규등록·재등록 폼도 `개월수 × 5,000` 으로 계산하고 있었다.

요금이 코드 네 군데에 흩어져 있어서 `admin-core.js` 에 **`LOCKER_MONTHLY_FEE = 5000`** 하나로 모으고
모두 그 상수를 쓰게 했다. 가격이 바뀌면 이 한 줄만 고치면 된다.

개월수를 고르면 금액이 자동으로 채워지는 곳:

| 화면 | 동작 |
|---|---|
| 신규등록 / 재등록 폼 | 원래부터 자동계산 (상수만 교체) |
| 락커 배정 모달 | 개월수 선택 시 금액 자동 (새로 추가) |
| 락커 연장 모달 | 연장 개월수 선택 시 금액 자동 (새로 추가) |
| 회원 상세 > 락커 등록 | 1·3·6개월 선택 시 금액 자동. 회원권 연동이면 기간에서 개월수를 되짚어 계산 (새로 추가) |

배정·연장 모달의 금액 placeholder 에 박혀 있던 `55000` 은 실제 요금이 아니어서
`개월수 × 5,000` 으로 바꿨다. `기타 (직접 설정)` 은 개월수를 모르므로 금액도 직접 넣는다.

회원권 연동으로 등록할 때는 `utils.js` 의 `monthsBetweenDates()` 로 개월수를 구해
락커 기록의 `months` 에도 남긴다 (락커 화면에 `-개월` 로 뜨지 않게).

## 홈 목록 6명 고정

`회원권 만료 임박` / `생일` 칸은 내용만큼 계속 늘어나고 있었다.
**6명까지 보이고 그 아래는 스크롤** 되도록 `max-height: 318px` (한 줄 ≈ 53px × 6)을 줬다.
스크롤바는 매출 그래프와 같은 얇은 스타일로 맞췄다.

## 테스트 데이터 (사용자 요청으로 남겨둠)

사용자가 테스트용으로 넣어달라고 해서 회원 7명이 로컬 DB에 들어 있다.

- `테스트회원` — 회원권 2026-09-17 ~ 2026-12-17 (락커 등록 테스트용)
- `만료임박1` ~ `만료임박6` — 만료일이 하루씩 밀린 6명, 생일도 임박

지우려면: `docker exec -i grove-pg psql -U postgres -d grove -c "TRUNCATE member_registrations RESTART IDENTITY; DELETE FROM members;"`

# 재등록 폼 락커 자동화 (같은 날)

회원 관리 > 등록 > **재등록** 에서 회원을 고르면 락커가 알아서 준비되게 했다.
모두 `frontend/public/js/admin-pricing.js` 안에서 처리한다.

## 1. 락커 자동 체크 + 번호 자동 채움

회원을 선택하면 `findRenewLockerId(m)` 이 쓸 번호를 고른다.

1. **지금 쓰고 있는 락커가 있으면** 그 번호
2. 없으면 **예전에 쓰던 락커가 지금 비어 있을 때만** 그 번호를 다시 제안한다
   (`locker_history` 를 최신순으로 훑어 `status='empty'` 인 첫 번째 락커)
3. 둘 다 아니면 제안하지 않는다 → 체크도 안 되고 번호칸도 빈 채로 둔다

**다른 사람이 그 락커를 쓰고 있으면 제안하지 않는다.** 원래 있던 "락커 입력칸 초기화" 블록을
고쳐 쓴 거라 코드가 새로 늘지 않았다 (항상 `checked = false` 로 꺼두던 것을 바꿨다).

`locker_history` 조회는 `LIMIT 200` 이라 아주 오래된 이력은 못 본다. 편의 기능이라 그대로 뒀다.

## 2. 회원권 기간을 바꾸면 락커 개월수도 따라옴

`syncRenewLockerMonths()` 를 새로 만들어 `onRenewPeriodChange()` 끝과
만료일 입력(`renew-end` 의 `onchange`)에서 부른다.

- 락커를 등록하기로 체크한 경우에만 동작한다
- `만료일 직접입력` 이면 `getRenewPeriod()` 가 날짜 차이로 개월수를 되짚어준다
- 개월수가 바뀌면 `calcRenewLockerAmount()` 로 금액(개월수 × 5,000)도 같이 다시 계산한다

## 검증

`findRenewLockerId` 소스를 그대로 떼어내 실제 서버 데이터로 돌렸다
(`node` 스크립트에서 `adminFetch` 만 끼워 넣는 방식 — 함수를 흉내 내지 않고 원본을 실행).

| 상황 | 기대 | 결과 |
|---|---|---|
| 30번을 쓰다 반납했고 지금 비어 있음 | 30 제안 | ✓ |
| 그 30번을 다른 사람이 쓰는 중 | 제안 안 함(null) | ✓ |
| 지금 30번을 쓰는 중 | 30 제안 | ✓ |

검증에 쓴 락커 배정·이력은 지웠다. 사용자가 요청한 테스트 회원 7명은 그대로 남아 있다.

# 전체 연결 검사 (오늘 작업 마무리)

오늘 건드린 것 전부를 놓고 **같은 이름·변수를 쓰는 것들이 실제로 연결돼 있는지** 기계적으로 훑었다.
검사 스크립트는 임시 폴더에서 돌렸고 레포에는 남기지 않았다.

## 검사 항목과 결과

| 검사 | 결과 |
|---|---|
| JS가 찾는 DOM id ↔ HTML에 있는 id | 불일치 없음 (문자열 조합 id는 오탐) |
| 인라인 onclick이 부르는 함수 ↔ 정의 | 불일치 없음 |
| 프론트가 부르는 API ↔ 백엔드 라우트 | 불일치 없음 |
| 같은 페이지에 로드되는 파일 간 전역 중복 선언 | 없음 |
| `ledger_entries` 컬럼 ↔ SQL이 쓰는 컬럼 | 일치 |
| `/api/ledger` 응답 키 ↔ 프론트가 읽는 키 | 일치 |
| 행 필드(date/category/name/amount/detail/fixed/ledger_id) | 일치 |
| `POST /api/ledger` 본문 ↔ 백엔드 구조분해 | 일치 |
| `PUT /api/lockers/:id` 본문 ↔ 백엔드 구조분해 | 일치 |
| `openMemberLockerModal` 호출 인자 4개 ↔ 정의 4개 | 일치 |
| `LOCKER_MONTHLY_FEE` 정의 파일이 사용 파일보다 먼저 로드 | 일치 |
| `PAYMENT_METHODS` 프론트 ↔ 백엔드 | 일치 |
| 지운 것(`stat-uniforms`, 운동복 서브탭, months 드롭다운)이 양쪽에서 사라졌는지 | 확인 |

## 검사에서 나온 진짜 문제 (고침)

### 1. 락커 환불 계산이 요금 상수와 끊겨 있었다

`admin-members.js` 의 환불 계산이 `monthsLeft(...) * 5000` 으로 하드코딩돼 있었다.
오늘 `LOCKER_MONTHLY_FEE` 로 모아놓고도 **여기 하나만 연결이 안 돼서**,
요금을 바꾸면 등록 금액은 바뀌는데 환불액만 옛날 값으로 남는 상태였다. 상수를 쓰게 고쳤다.

### 2. 매출 관리 탭으로 돌아왔을 때 가계부가 안 갱신됐다

`openPage('revenue')` 는 매출 내역만 다시 읽었다. 가계부 탭을 열어둔 채 회원 등록이나 환불을
하고 돌아오면 **가계부는 옛날 숫자를 그대로 보여줬다.** 가계부 탭이 열려 있으면 같이 읽도록 했다.

## 되돌린 것 — 운동복 필터 옵션

검사 중에 "과거 운동복 매출은 목록에 뜨는데 구분 필터로는 못 고른다" 는 비대칭을 발견하고
필터 옵션을 임의로 복구했는데, **사용자 지시 위반이었다.** 사용자의 "과거건은 건드리지 마" 는
데이터를 지우지 말라는 뜻이었지 운동복 UI를 되살리라는 뜻이 아니었다. 다시 제거했다.

**과거 운동복 매출 데이터는 그대로 집계에 남아 있고, 화면에서 운동복을 고를 수 있는 곳은 없다.**

## 보고만 하고 안 건드린 것

- **가계부 지출 항목의 `환불`** — 회원권 환불은 자동으로 지출에 잡히는데, 여기에 수기로 또 넣으면
  같은 환불이 두 번 계산된다. 물품 환불 같은 걸 적으려면 필요할 수도 있어 사용자 판단을 기다린다.
- **가계부 매출의 `회원권` vs 자동 집계의 `회원등록`** — 사실상 같은 것을 두 이름으로 부르고 있어
  매출 구분 필터에 둘 다 들어가 있다.
- **회원 목록의 `운동복` 컬럼(`th-uniform`)** — 아직 화면에 보인다. 이번 요청 범위 밖이라 뒀다.
- `d-start`, `reg-detail`, `today-schedule-list` — JS가 찾지만 HTML에 없는 id 3개.
  전부 `if (!el) return` 으로 막혀 있어 오류는 안 난다. 오늘 작업과 무관한 기존 죽은 코드.
- 락커 이력 조회 `LIMIT 200` — 재등록 번호 제안이 아주 오래된 이력은 못 본다.

## 더미데이터 전량 삭제

로컬 DB의 모든 업무 테이블을 비웠다. 회원·등록·락커 배정·락커 이력·운동복·가계부·신청·계약서·
홀딩·문자로그 전부 0건이고, 락커 152개는 전부 `empty` 로 되돌렸다.
빈 상태에서 홈·가계부·매출·락커 화면이 모두 정상 응답하는 것을 확인했다.

# 홈 업데이트 소식(패치노트) 게시판 · 잔재 정리 (2026-09-18)

## 업데이트 소식 게시판

홈 최하단에 기존 카드와 같은 모양의 카드를 하나 더 두고, 깃 커밋 기록을 사람이 읽을 수 있게
추려서 한 줄씩 나열했다. 줄을 누르면 팝업이 뜬다.

- **목록 한 줄**: `버전` `날짜` `제목` `규모 배지`
- **팝업 안**: 요약 한 문단 → **주요 변경점** 목록 → **이렇게 써보세요** (직접 눌러볼 순서)

게임 패치노트처럼 "이 버튼을 눌러 이 값을 넣어보세요" 수준까지 적어서, 시스템을 모르는
사람도 따라 하며 확인할 수 있게 했다.

### 버전 계산

깃 커밋 27개(머지 커밋 제외)를 주제별로 12덩어리로 묶고, 오래된 것부터 더해 올라갔다.

| 규모 | 증가폭 |
|---|---|
| 대격변 | +1.0.0 |
| 중간급 | +0.1.0 |
| 소규모 | +0.0.1 |

자리올림 없이 그대로 누적한다(그래서 뒷자리가 계속 커진다). 결과는 `1.0.0` → 현재 **`2.7.3`**.

처음 계산할 때 항목을 합치면서 단계 수가 틀어져 뒷자리가 1씩 밀렸다.
**계산을 코드로 검증**해서(규모 목록으로 버전을 다시 만들어 비교) 8건을 바로잡았다.
새 항목을 추가한 뒤에도 같은 방식으로 다시 검산하면 된다.

### 저장 방식

DB를 쓰지 않는다. `frontend/public/js/admin-patchnotes.js` 의 `PATCH_NOTES` 배열이 전부다.
새 업데이트가 나오면 배열 맨 위에 한 덩어리를 추가하면 된다 (관리자 CRUD 화면은 만들지 않았다 —
글이 한 달에 한두 개라 코드에 적는 편이 싸다).

## 사용자 지시로 삭제한 것

- **회원 목록의 `운동복` 컬럼** — 헤더·셀·필터·정렬 분기까지 전부 제거.
  컬럼이 8칸에서 7칸으로 줄었는데 빈 목록 `colspan` 이 8로 남아 있어서 같이 고쳤다.
  **레포의 모든 표에 대해 헤더 칸 수와 colspan 이 맞는지 한 번에 검사**했고 나머지 13개 표는 정상.
- **죽은 DOM 참조 3개** — `d-start`(admin-core.js), `reg-detail`(admin-members.js),
  `today-schedule-list`(admin-schedule.js). 마지막 것은 아무도 부르지 않는 함수라 통째로 지웠다.

운동복 환불 관련 코드(`refund-uniform-row` 등)는 남겼다. 활성 운동복이 있을 때만 보이는데
서비스가 끝나 활성 건이 없으므로 화면에 뜨지 않는다. 환불 로직을 건드리는 일이라 요청 범위 밖으로 뒀다.
