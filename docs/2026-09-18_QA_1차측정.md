## 찾은 결함 — 심각한 순서

### 1. 저장형 XSS (고침 전 · 가장 위험)

회원 이름에 `<img src=x onerror=...>` 같은 것을 넣고 환불 창을 열면 **그 스크립트가 실행된다.**

`escapeJsAttr()` 는 `<` 를 `&lt;` 로 바꾸지만, 그 값이 `onclick="..."` 속성 안에 들어가면
**브라우저가 속성값의 HTML 엔티티를 먼저 되돌려서** JS 에는 `<` 그대로 전달된다.
그것이 `innerHTML` 로 들어가면 진짜 태그가 된다.

```
저장된 이름   <img src=x onerror=alert(1)>
HTML 속성     onclick="openMemberRefund(1,'&lt;img src=x onerror=alert(1)&gt;')"
JS 가 받는 값  <img src=x onerror=alert(1)>      ← 엔티티가 되돌려졌다
innerHTML     <b><img src=x onerror=alert(1)></b>  ← 실행된다
```

같은 자리의 `admin-facility.js` 는 `escapeHtml(name)` 을 쓰고 있어 안전하다. 한쪽만 빠졌다.

## 1. 저장형 XSS — 3곳

회원 이름처럼 사람이 적은 글자가 `onclick="fn('${escapeJsAttr(name)}')"` 로 실려 나가면,
**브라우저가 속성값의 HTML 엔티티를 되돌려서** 함수는 `<img ...>` 를 그대로 받는다.
그것을 `innerHTML` 에 넣으면 진짜 태그가 된다.

- `admin-members.js` 환불 창의 이름 → `escapeHtml` 로 감쌈
- `admin-holding.js` 홀딩·특별연장 선택 표시의 만료일 2곳 → 같이 감쌈

**회귀 검사도 같이 만들었다** — 속성으로 받은 인자가 `innerHTML` 로 들어가는 자리를
소스에서 찾아내는 검사를 `probes/i_injection.js` 에 넣었다. 다시 생기면 바로 잡힌다.

## 2. 51개 API 의 500 — 한 곳만 고쳤다

경로 51개에 검사를 하나씩 넣는 대신, **전역 오류 처리기 한 곳**에서 DB 오류 코드를 4xx 로 바꾼다.

| `22003` 숫자 범위 초과 | 400 숫자가 너무 큽니다 |
| `22001` 길이 초과 | 400 입력이 너무 깁니다 |

## 3. 회원 삭제가 딸린 기록을 안 지웠다

`members` 와 `member_registrations` 만 지워서 **락커 배정과 그 매출 기록이 남았다.**
없는 회원의 락커 요금이 매출에 계속 잡히고, 락커는 사용 중인 채로 묶여 있었다.

한 트랜잭션 안에서 정리한다.

- **락커** — 1~152번 고정 행이라 지우지 않고 `비어있음` 으로 되돌린다
- **8개 표** — 락커 이력 · 운동복 · 운동복 이력 · 횟수 사용 · 홀딩 · 특별연장 · 메시지 · 등록이력
- **계약서** — 서명이 든 문서라 지우지 않고 **연결만 끊고 `미등록` 으로** 되돌린다
- 없는 회원을 지우면 404

확인 15개 통과: 붙였다 지운 뒤 **매출·지출·락커 수가 전부 삭제 전 값으로 돌아온다.**

## 5. 같은 이름으로 동시에 누르면 여러 명이 만들어졌다

"이미 있나 확인 → 없으면 넣기" 사이의 틈 때문이다. 확인과 삽입 사이에 다른 요청이 끼어들면
둘 다 '없음' 을 보고 둘 다 넣는다.

**DB 에 유일 인덱스(`members_name_unique`)를 걸어** DB 가 직접 막게 했다.
회원 로그인이 이름으로 이뤄지므로 이름은 원래 유일해야 한다.
라우트에서는 그 오류(23505)를 받아 **원래와 같은 안내 문구**를 돌려준다.

확인: 같은 이름으로 **동시에 5번** 눌러도 1명만 만들어지고, 나머지 4건은
"이미 OOO 님이 등록되어 있습니다" 로 거절된다.

## 수정하면서 새로 생긴 지적도 같이 잡았다

3번을 고치면서 `DELETE FROM ${table} WHERE ...` 반복문을 썼더니 QA 가 두 가지를 잡았다.

- **SQL 에 이름을 문자열로 붙인다** (I) — 지금은 고정 목록이라 안전하지만, 나중에 그 변수가
  밖에서 오면 막을 방법이 없다. 표 8개를 **하나씩 적어** 패턴 자체를 없앴다.
- **반복문 안에서 DB 를 두드린다** (Q) — 같은 수정으로 사라졌다.

6줄 줄이자고 SQL 주입 검사에 예외를 만드는 것보다, 예외 없는 검사를 유지하는 편이 낫다.

## 1. 홀딩 걸었다 풀면 락커가 공짜로 늘어나던 것

거는 쪽은 활성 락커를 **무조건** 늘리고, 푸는 쪽만 "홀딩 신청일보다 나중에 시작한 락커는 안 깎는다"
는 조건을 봤다. 그래서 **시작일이 미래인 락커**(재등록 회원에게 흔하다)는 걸었다 풀 때마다
기간이 며칠씩 남았다.

조건을 `isAffectedByHolding()` 하나로 만들어 **거는 쪽과 푸는 쪽이 같은 함수를 쓰게** 했다.
따로 있으니까 갈라졌던 것이다.

확인 7개: 이미 시작한 락커는 밀리고 풀면 정확히 돌아온다 / 아직 시작 안 한 락커는 밀지도 깎지도
않는다 / **걸었다 풀기를 5번 반복해도 기간이 그대로다** / 회원권 만료일과 쓴 홀딩도 제자리.

## 2. 달력에 없는 날짜를 말없이 오늘로 바꾸던 것

`2026-02-31` 을 넣으면 거절하지 않고 **오늘 날짜로 바꿔** 저장했다.

이제 `달력에 없는 날짜입니다 — 2026-02-31` 로 돌려보낸다. 윤년도 제대로 가린다
(2026-02-29 거절 / 2024-02-29 통과). **날짜를 비워 보내면 오늘로 넣어 주는 편의는 그대로 둔다** —
비운 것과 잘못 친 것은 다르다.

문구에서 날짜 뒤 조사는 뺐다. 끝 숫자에 따라 은/는이 갈리기 때문이다(`2026-02-31은` / `2026-02-22는`).

## 4. 트랜잭션 — 4곳 중 2곳은 오탐이었다

| 곳 | 판정 |
|---|---|
| 신청 접수 (`/api/applications`) | **오탐** — 문자 발송 로그는 일부러 떼어 놨다. 문자가 실패해도 신청은 접수돼야 하므로 묶으면 오히려 틀린다 |
| WOD 등록 (`/api/wods`) | **오탐** — if/else 라 둘 중 하나만 돈다 |
| 직원등록 (`/api/contracts`) | **진짜** — 회원 INSERT + 계약서 연결을 한 트랜잭션으로 묶음 |
| 계약서 등록처리 (`/api/contracts/:id/link`) | **진짜** — 같은 행을 두 번 고치던 것을 한 문장으로 |

탐지기도 고쳤다 — SQL 문자열 개수가 아니라 **실제로 DB 를 부르는 횟수**로 세고,
`try/catch` 로 감싼 곁가지와 `if/else` 분기는 빼고 센다.

## 5. 의존성 취약점 — 4건 중 2건 제거, 2건은 해당 없음

| 패키지 | 심각도 | 어디서 | 판정 |
|---|---|---|---|
| `brace-expansion` | **높음** | ejs → jake → filelist → minimatch | 빌드 도구라 요청 처리에 안 쓰인다. **비파괴 수정으로 제거** |
| `qs` | 보통 | express (쿼리스트링 해석) | **실제로 사용자 입력이 지나간다. 비파괴 수정으로 제거** |
| `uuid` | 보통 | exceljs → uuid 8.3.2 | **해당 없음** — 취약점은 v3/v5/v6 에 `buf` 를 넘길 때인데, exceljs 는 `uuidv4()` 만 쓴다 |

`npm audit fix --force` 를 하면 **exceljs 가 4.4.0 → 3.4.0 으로 내려가 매출 엑셀이 깨진다.**
해당 없는 취약점 때문에 쓰는 기능을 깨뜨리지 않는다. 고친 뒤 엑셀 내려받기(11KB xlsx) 정상 확인.

`확인 필요` 로 빼도록 고쳤다.

## 7. escape 확인 16곳 — 판정하다 6곳을 더 찾았다

16건을 하나씩 봤다. 숫자·날짜·사진 데이터·고정 문구는 안전했지만, **DB 에서 오는 글자가 섞여 있었다.**

| 파일 | 무엇이 |
|---|---|
| `visit.js` | 휴관일·이벤트 **제목**, **수업명**(화면 + onclick 인자 양쪽), 메모, 신청 화면 상단 안내 |
| `index.js` | 달력의 공지 **제목**, 공지 팝업의 제목·내용·메모 |
| `admin-pricing.js` | **요금제 이름** (드롭다운과 표) |
| `admin-schedule.js` | **수업명**, 시각(표 + 버튼 인자) |

`index.js` 는 **같은 파일 안에서 어떤 줄은 escape 하고 어떤 줄은 안 했다.** `visit.js` 는
`index.js` 의 같은 코드를 복사하면서 escape 만 빠졌다. 복사하며 갈라진 전형적인 모습이다.

특히 **수업명이 `onclick` 인자로 들어가는데 escape 가 없었다** — 수업명에 작은따옴표 하나만 있어도
버튼이 통째로 안 먹는다. 방문 페이지는 **로그인 없이 누구나 보는 화면**이다.

### 탐지기의 구멍도 막았다

이것들이 지나간 이유는 탐지기가 `innerHTML = \`...\`` 만 보고
**`innerHTML = xs.map(x => \`...\`)` 안쪽을 안 봤기** 때문이다. 목록을 돌며 만드는 문자열은
거의 전부 DB 값인데 그걸 통째로 놓쳤다. 이제 둘 다 본다.

# 보류한 것 (2026-09-19)

## 관리자 로그인 문자 2단계 인증 — 보류

`/admin` 진입을 바꾸는 방법을 알아보다가 나온 이야기다. 정리하면 이랬다.

- **주소를 숨기는 것은 대책이 아니다.** `/admin` 을 바꿔도 로그인은 `/api/admin/login` 으로 가므로
  공격하는 쪽은 화면을 안 거친다. 흔한 주소를 긁는 봇 소음만 줄어든다.
- **실제로 위험을 줄이는 것은 2단계 인증뿐이다.** 비밀번호가 새도 못 들어오게 하는 유일한 방법이다.
- 방식은 **비밀번호 → 문자 6자리 → 그 기기를 7일간 기억** 이 적당하다. 알리고 문자가 이미 붙어 있어
  새로 만들 것이 거의 없고, 문자도 사람당 월 4~5통이라 비용이 사실상 없다.

**사용자 판단으로 보류했다.**

> "지금은 회원규모도 적고 코치 1명에 직원 1명이니까 이렇게까지 할일은 아닌것같다"

맞는 판단이다. 지금 위험은 "누가 비밀번호를 흘리느냐" 하나인데, 아는 사람이 셋이고 다 아는 사이다.
5회 실패 시 10분 잠금이 있어 무차별 대입은 사실상 막혀 있다.

### 다시 꺼낼 조건

아래 중 하나라도 생기면 그때 붙인다.

- 관리자 화면을 쓰는 사람이 **넷 이상**이 될 때
- **알바처럼 오래 안 있을 사람**에게 계정을 줄 때
- 코치나 직원이 **그만둘 때** (비밀번호를 바꿔도 누가 알고 있었는지 추적이 안 된다)
- 비밀번호가 샜다고 **의심되는 일**이 생겼을 때

### 그때 같이 설계해야 하는 것 (잊지 않도록)

- **사장님 계정에는 전화번호가 없다.** `ADMIN_PASSWORD` 하나로 들어오는 구조라 받을 번호가 없다.
  `.env` 에 번호를 하나 넣는 것이 가장 간단하다.
- **비상 진입로가 반드시 필요하다.** 작은 시스템에 2단계 인증을 붙일 때 실제로 나는 사고는
  해킹이 아니라 **본인이 잠기는 것**이다. 알리고가 죽거나, 문자 요금이 떨어지거나, 번호를 오타로
  넣어두면 영업 중에 관리자 화면이 안 열린다. 미리 뽑아 둔 비상 코드 같은 우회 수단이 있어야 한다.
- **로컬에는 알리고 값이 없다.** 값이 없으면 문자 대신 화면에 코드를 띄우도록 해두면
  로컬에서 전 과정을 시험할 수 있다.

## 성능 개선 (인덱스·N+1·조회 상한) — 보류

같은 이유로 미뤘다. 회원이 6명이라 체감이 없다. **회원 100명을 넘을 때** 하기로 했다.
